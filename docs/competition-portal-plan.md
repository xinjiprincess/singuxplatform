# 比赛与临时专用平台实施计划

日期：2026-09-29。方案版本：0.2。状态：专用入口核心功能已实现，本地联调中；未发布服务器。下文保留总体目标，实际交付范围以下节及调试记录为准。

## 本轮实施范围

- 官网与专用入口共用构建产物；Umi 启动时根据已验证入口设置 basename，提供 `/zhichuangbei/login` 和前缀内工作区。不会复制一套后端进程或业务数据。
- 新增 `platform_portal`、`platform_portal_audit`，记录绑定租户、品牌、启停、开放时间及变更原因。入口绑定租户不可在线改写；编辑使用旧配置比对防止覆盖。
- `/platform/portals` 由平台管理员创建和编辑入口；现有 `/platform/tenants` 管理成员及租户。首期为管理员分配成员资格，未实现公开赛事报名、名单导入或专门报名审核页面。
- 比赛用户名密码登录直接验证目标租户成员关系，签发绑定 `portalSlug`、租户、成员版本的会话；不进入企业选择。比赛会话禁止平台管理、企业切换和企业申请接口。
- 品牌采用文本、受限站内图片路径及十六进制主题色，不接受任意脚本/HTML。图片暂由路径配置，未新增素材上传管理器。未提供赛事主办方 Logo，初始沿用平台 Logo。
- 官网与各入口的 Token、用户、租户配置及主题缓存分键，Cookie 使用独立名称。它们仍然同源，不构成浏览器安全沙箱。
- **API 实现调整**：保留 `/api/...`，不新增路径重写代理。前端为同源 API 添加 `X-Singu-Portal` 路由提示；后端重新解析入口、核验成员、校验 JWT 的入口和租户。这个客户端头不具有授权效力，去掉或伪造头不能让已签发令牌跨入口使用。普通请求、fetch 流式客户端和 XHR 上传均带提示；WebSocket、分享、原生图片下载等全部业务链路仍需逐项验收。
- 本地新租户需导入仓库自带权限模板 `1.4`，仅初始化菜单、角色和资源定义；不复制官网作品。修复了旧角色/组绑定把跨企业成员误判为不存在的问题。
- 本轮不声称完成跨团队业务数据、对象存储、向量搜索、后台任务、长连接撤销、MCP/沙箱/网页应用全链路隔离和负载验收。真实比赛开放前，这些仍是发布门槛。
- 排名、评分、证书、真实支付及独立移动客户端不在范围内，也不作为后续待办。

## 1. 目标和边界

- 官网 `https://www.ciyuancenter.cc` 的现有登录、企业选择、功能和导航保持不变。
- 新增 `https://www.ciyuancenter.cc/zhichuangbei`，用于“2026华为智创杯·AI智能体开发大赛”的“智能体搭建与应用开发实践平台”。名称按用户提供记录，正式展示素材和主办方标识发布前确认授权。
- 比赛入口有独立登录页、Logo、favicon、配色、名称和导航路径；登录后不出现企业选择、创建企业或企业切换页面。
- 复用同一代码库和前后端镜像，保留智能体、工作流、MCP、沙箱、网页应用等核心功能及原有权限控制，不复制一套比赛业务代码。
- 后续学校、企业临时使用时，通过管理端创建专用入口、绑定租户和有效期，不另开代码分支。
- 用户原文的 `wwww` 暂按笔误处理，使用现有三条 w 主域名；路径入口不需要新增 DNS 或独立证书。

“专用平台”是入口与租户隔离，不是操作系统沙箱。执行不可信代码仍须使用受限容器；同源路径也不是浏览器安全边界。

## 3. 架构选择

采用“共享应用服务 + 专用入口 portal + 固定租户 + 按需执行容器”。首期每个专用入口绑定一个独立租户；官网不绑定比赛租户。比赛租户内以空间及成员授权区分个人或团队，禁止全体参赛者默认读取全部作品。

普通 CRUD、鉴权、静态资源、数据库进程、Redis、对象存储基础设施可共享，但所有业务数据、对象键、缓存、任务、搜索及向量检索必须落实租户边界。若隔离审计不通过，不开放真实比赛数据；需要临时隔离部署时仍复用相同镜像，使用独立数据库/凭据/存储，不将额外占用隐瞒为轻量方案。

独立前后端副本不是首选：其维护、内存和升级成本随活动数量增长。强安全隔离或专属 SLA 场景再启用独立部署档位。

## 4. URL 与前端启动

| 官网 | 比赛专用入口 |
| --- | --- |
| `/login` | `/zhichuangbei/login` |
| `/space/{id}/develop` | `/zhichuangbei/space/{id}/develop` |
| 原工作流、智能体、网页应用路由 | 保持原路径结构，仅增加 `/zhichuangbei` 前缀 |
| `/api/...` | `/zhichuangbei/api/...`，由网关映射到同一后端 |

1. 使用入口注册表匹配规范化的首段路径，只匹配已注册 slug，不将任意路径推断为租户。保留 api、login、platform、space、静态目录等关键字。
2. 在应用初始化、鉴权和品牌渲染前解析入口；`/zhichuangbei` 统一跳转到带尾斜杠的入口，随后按会话状态进入登录或工作区。未知/停用入口显示明确页面，不回退官网租户。
3. 新增统一 PortalContext 和导航助手，集中生成登录跳转、菜单、面包屑、分享地址、上传、SSE、WebSocket 和 API 地址。审计硬编码 `/login`、window.location、history.push、链接和预览路径。
4. Umi 路由采用构建期生成共享路由的官网及参数化入口版本，或经小型验证后使用启动时 basename；不得假设当前 Umi 支持任意运行时 base。两者均使用同一构建产物。首个技术验收就是官网/比赛深链接刷新均正常。
5. 带 hash 的公共 JS/CSS 可共用根路径，API 与私有内容禁止公共缓存。SPA 回退不能吞掉缺失 JS 的 404。比赛路径跳转不得丢前缀。
6. 网关清除客户端自带的入口转发头，按已验证路径注入规范入口标识；后端只信任受控网关。不得以 Referer 或任意客户端 tenantId 鉴权。访问内部端口不得绕过上下文验证。

## 5. 登录和参赛资格

比赛入口解析品牌 → 用户名/邮箱等现有认证方式 → 后端核验比赛成员资格 → 签发绑定入口和租户的业务会话 → 比赛工作区。无需企业选择，但仍需认证和授权。

- 默认推荐邀请或审核入场；未加入者显示“申请参赛/等待审核”，不跳转官网企业选择。是否开放自主注册由入口配置控制，不能默认所有账号自动成为成员。
- 若采用公开报名，收集最少必要的姓名、学校/单位及联系方式，明确用途、同意与保留时间；报名通过后事务性创建成员资格，重复提交幂等。
- 已有官网账号可复用身份，但不能拿官网或其他比赛令牌直接访问本比赛。签发会话必须验证入口、租户、成员状态及有效期。
- 令牌/服务端会话绑定 portalId、tenantId、userId、membership/version、有效期；比赛停用、成员移除和权限变更撤销后续访问，并处置已建立长连接。
- 比赛会话不能调用企业切换、创建企业、其他入口管理接口；限制在服务端实施。需要返回官网时重新建立官网上下文，不静默沿用比赛权限。
- 缓存和令牌使用 host + portalId + tenantId + userId 命名空间；标签页固定自身入口，广播按入口分组，不让比赛注销清掉官网会话。上下文变化取消旧请求、长连接，丢弃晚到响应。
- localStorage 分键和 Cookie Path 不是安全隔离。必须治理 XSS、使用 CSP，并让生成网页和不可信预览运行于独立 origin，不能放在平台官网同源执行。要求浏览器级隔离时采用子域名入口。

## 6. 配置和管理

建议逻辑实体 `platform_portal`：id、slug（唯一）、tenant_id、display_name、type、status、starts_at、ends_at、brand_config、login_policy、quota_policy_ref、version、created_by。先查已有表后确定复用或迁移，不复制用户、智能体、工作流表。

品牌配置限于受校验的文本、受管素材引用和设计 token，不允许任意 HTML、JS 或外部脚本。公共配置仅返回品牌、入口状态和必要登录方式；不返回密钥、成员列表及内部部署信息。

管理端增加“专用平台”：创建、预览、启停、有效期、绑定租户、品牌、报名策略、审核、额度、用量及审计。所有操作使用独立平台管理员权限。比赛管理员只管理本比赛成员及授权资源，不能成为平台超级管理员。

现有免费版禁止自定义 Logo/域名的规则保留。比赛品牌使用平台运营方显式授予、可到期的专用入口权益，不允许免费租户通过创建入口绕过付费规则。更换绑定租户首期禁止在线直接操作，需停用入口并完成迁移审计。

建议接口（均待实现/复用核对）：

- `GET /api/public/portals/{slug}`：公开入口配置。
- `POST /api/session/portal/select`：已有身份凭证换取目标入口会话，服务端核验资格。
- `GET/POST/PATCH /api/platform/portals...`：平台管理、品牌和启停。
- 入口作用域下的报名、审核接口：复用已有申请机制，明确目标入口与租户，不混用企业创建审批。

## 7. 资源与生命周期

- 不为每个入口复制 MySQL、Redis、向量库或常驻后端；共享静态资源和镜像层。
- 沙箱按实际会话创建，按 tenant/user/project 标记归属；限制 CPU、内存、PID、磁盘、网络出口、并发和运行时长，空闲回收计算容器但保留项目持久化卷。
- 预热池规模、空闲阈值和单租户并发均配置化；首期默认不建立每租户常驻预热池。
- MCP 按租户/凭据隔离进程及缓存；只在确认无状态且无凭据混用风险时共享实例。不能为了省资源复用不同租户的进程环境。
- 模型调用限并发、请求速率、Token 和预算，预留/结算/释放幂等；公平排队，防止比赛流量挤占官网。管理端可修改上限，但不承诺未经压测的并发人数。
- 到期建议只读归档、允许授权导出，停止新建执行任务；通知管理员后按保留策略清理，不在到期时直接删作品。备份、数据库迁移和回滚独立管理。
- 实测空载内存、单沙箱峰值、冷启动时间、队列等待和模型费用后确定参数；没有测量前不宣称节省比例。

## 8. 实施顺序和交付门槛

1. 基线审计：记录官网功能、权限与资源消耗，列明隔离缺口；确定参赛报名方式与数据保留策略。
2. 入口基础：注册表、路由验证、公开品牌、独立登录 UI；官网回归通过，未知入口不串品牌。
3. 会话与资格：固定租户会话、禁止切换、审批和撤销；跨入口/跨租户负例全部通过。
4. 功能适配：智能体、工作流、文件、MCP、SSE、网页应用预览逐项验证前缀与资源权限；不能只验登录页。
5. 管理和限额：入口生命周期、运营授权、资源限额、公平队列、到期归档及监控。
6. 本地 Docker 验收：同一前端/后端镜像同时服务官网与两个测试入口；保存测试结果和可回滚配置。
7. 发布另行确认：不在本轮自动更新生产，不强行对未完成隔离项放行。

明确不需要赛事排名、评分、证书颁发、真实支付或独立移动客户端；这些不属于本项目专用平台范围，也不列入后续待办。已有平台功能保持原状，不因本条删除原有业务。
